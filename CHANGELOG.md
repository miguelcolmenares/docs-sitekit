## [Unreleased]

### Added

- **Brand logos: `icon: "brand:<slug>"` in the config.** The kit ships 11 logos (Astro, Docker, GitHub, GitLab, Next.js, Node.js, npm, React, Tailwind CSS, TypeScript and Vercel) as path data, generated by `npm run build:brands` from `simple-icons` pinned to 16.36.0, a development dependency of the kit only. A logo is an inline SVG filled with `currentColor`, hidden from assistive technology unless `Icon` gets a `label`, and it asks nothing from any host, so a generated site has no new dependency. An unknown slug fails the build with the slug and the closest brands. The licence gate fails the script for an icon that is not CC0 unless it is on `scripts/brands/allowlist.json` with its licence, author and attribution, which then go to `THIRD_PARTY_NOTICES.md`; PHP (CC BY-SA 4.0) and AWS are not shipped. A logo the kit does not have is added as `brands/<name>.svg` next to the config and used as `brand:custom/<name>`; only plain `<path>` shapes are accepted. The header shows a repository button with the logo of the host (GitHub or GitLab, else a plain icon) and its name, 44 px tall, in the open menu on a phone, and the footer link has the logo too. A site generated earlier keeps its own copy of the template, so it gets this after `Icon.tsx`, the `domain/brands` folder, `customBrands.ts`, `config.ts` and the changes in `loadSite.ts`, `SiteHeader.astro`, `MobileMenu.tsx`, `SiteFooter.tsx` and `BaseLayout.astro` are copied from this version. See `docs/brand-logos.md`.
- **An "Edit this page" link and the date of the last change.** The `editLink` key (`enabled`, `branch`, `host`) puts a link at the foot of every page to its source file on the repository host: `{repository}/edit/{branch}/{path}` on GitHub, with the GitLab and Bitbucket forms too. The host is found from `site.repository`, `host` is for a repository on a domain of its own, and an unknown host turns the link off with a message in the build and in `sitekit check`, never a broken address. The path includes the folder of the sources inside the git repository, so a site in a subfolder gets the right address. The `lastUpdated` key shows the date of the last commit that changed the file itself, read with `git log` at build time, as a `<time datetime>` element. In a shallow clone, or outside git, no dates are shown and the build says why, and `sitekit check` warns when the clone is shallow. The link is a 44 px target and the line reaches WCAG AA in both themes. `sitekit init` turns both on for a new site and writes `fetch-depth: 0` in the workflow it generates. A site without the keys does not change, and `sitekit upgrade` adds both with `enabled: false`. The component is `PageInfo`, and `sitekit add page-info` restores it. A site generated earlier gets the line after `PageInfo.tsx`, `DocPage.astro`, `loadSite.ts`, `gitHistory.ts`, `buildPageMeta.ts`, `editLink.ts`, `lastUpdated.ts` and the change in `config.ts` are copied from this version. See `docs/edit-link.md`.
- **A filter bar for the index pages.** A page can have `tags` in its frontmatter, a list or a comma separated string. When any page of an index has a tag, the index shows a text field and one toggle button per tag above its cards. The cards that do not match get the `hidden` attribute, a polite status line says "N of M shown.", and a state with no match says so and offers "Clear filter". The state is in the address, `?tag=ui&q=card`, so a filtered view can be shared and the back button works. Without JavaScript every card is shown and the bar is hidden, and an index without tags does not change. The controls are 44 px high, with `aria-pressed` on the tags. The matching is a pure function in the domain layer, and `sitekit add catalog-filter` restores the files. A site generated earlier keeps its own copy of the template, so it gets the bar after `Document.tags`, `buildDocuments.ts`, `CollectionIndex.astro`, `ItemCard.tsx` and the files of `catalog-filter` are copied from this version. See `docs/components.md`.
- **Code blocks with a title, highlighted lines, diff lines and a copy button.** The options go after the language in the fence, which GitHub ignores: `ts title="src/config.ts" {2,4-6}`. A title is a caption bar over the block. The lines in the braces have a tone and a bar on their left edge. A line that ends with a `[!code ++]` or `[!code --]` comment, or a line of a `diff` block that starts with `+` or `-`, is shown as added or removed, with a sign as well as a tone, so color is not the only cue. The markers are taken out of the code. Every block has a copy button, a real button named "Copy code" with a 44 px target and a focus ring, that copies the text of the code (not the markers, and not the signs drawn in the margin) and says "Copied" in a polite status region. The button is written hidden and shown by a script of about 540 bytes that ships in the page and makes no request, so without JavaScript the block still reads. A long line scrolls inside the block, and a block with no options looks as it did. It is built on the Shiki transformers of the markdown package, so there is no new dependency. The tones are three new color tokens in both sets, `code-highlight`, `code-add` and `code-remove`, and the contrast tests check them against every token color of both code themes. A site generated earlier keeps its own copy of the template, so it draws these blocks only after the files that `docs/code-blocks.md` lists are copied from this version. See `docs/code-blocks.md`.
- **A `StatRow` component for a few numbers with their labels.** Two to five items, each a value, a label and an optional note, as a description list so the label and the value are read together. The value is the large text in the mono face and wraps when it is long. The grid has explicit tracks, one column on a phone, and it chooses no status color. The home page shows it when `sitekit.config.json` has a `stats` key (two to five items, or none), and a site without the key does not change. `sitekit add stat-row` restores it. See `docs/components.md`.
- **Search.** A header button, Ctrl K or Cmd K, and the slash key open a dialog that searches the title, headings and text of every page, and opens the section that matched. The search code and the index load on first use, and `search.enabled` in the config turns it off. `sitekit check` verifies that the index lists every page. Typo tolerance is not in this version.
- **A light theme, with a switch in the header.** The site stays dark by default. `theme.default` in `sitekit.config.json` takes `dark`, `light` or `system`, and an invalid value fails the build with the key named. A visitor's choice is saved in the browser and wins over the default, and the theme is applied before the first paint. The light set is a second set of colors in `design/tokens.json`, with the same keys as the dark one, and a test fails when the keys differ. Code blocks have a light highlighter theme. A site generated with an earlier version keeps its own `design/tokens.json`, which has no light set, so it stays dark until it adds one.
- **An `llms` key for `llms.txt`.** With `enabled`, the site writes `llms.txt` at its base: an H1 with the name, the description, one H2 per collection with absolute links and descriptions, and `## Optional` for the collections listed in `optional`. With `markdownPages`, each page also has a Markdown copy at its address with `index.html.md` after it, and the page links to it. `sitekit init` turns it on for a new site, and a site without the key does not change. It is a community proposal, not a search feature. See `docs/llms.md`.
- `sitekit check` verifies `llms.txt` when it is on: the H1, every link, every page listed, the Markdown copies, and the credential and internal host scan.
- **Callouts written in markdown.** A blockquote that starts with `> [!NOTE]`, `> [!TIP]`, `> [!IMPORTANT]`, `> [!WARNING]` or `> [!CAUTION]` on its own line becomes a callout, the alert syntax that GitHub renders too. It is plain HTML with `role="note"`, a hidden icon and a visible label, so it needs no JavaScript, and the tones come from the existing color tokens. A callout can hold paragraphs, lists and code, and can sit in a list item. A blockquote without a marker, an unknown marker such as `[!NOTES]`, and a marker in code are left as they are. The `Callout` component has the same five kinds, `role="note"` and a colored left edge, and the docs have a new page, Callouts. A site generated earlier keeps its own copy of the template, so it renders callouts only after `callouts.ts`, `calloutIcons.ts`, `remarkCallouts.ts`, the change in `renderMarkdown.ts` and the callout styles of `prose.css` are copied from this version. See `docs/callouts.md`.
- **`sitekit upgrade`, to bring a generated site up to the installed kit.** For each file in `site/.sitekit.json` it compares your file, the version it was written from (by hash) and the kit's file. A file you did not edit and the kit changed is replaced. A file you edited and the kit did not change is kept. A file you edited and the kit changed is left as it is, with the new version written next to it as `<file>.sitekit-new`, so your file is never lost. A file that is new in the kit is added. `--dry-run` prints the report and writes nothing, and the upgrade is a dry run by default when the working tree has uncommitted changes, unless you pass `--apply`. It never writes `docs/`, your other content, the deploy workflow or files that are not in the lock, and it adds only the options that do not exist yet to `sitekit.config.json` (`theme`, `search`, `llms`), with the value that keeps the site as it was. The lock is rewritten for the files that were replaced or added. The package name and description of a site are kept. See `docs/upgrading.md`.
- **Content findings in `sitekit check` and in the build.** The markdown is read as data and each problem is reported as `docs/guide.md:42: warning: ...`, with a severity, the file and the line of the link, image, heading or key: a relative link to a file that does not exist or that you excluded, a link to a heading that is not in the target page, an image that does not exist, a frontmatter key the kit does not read, an `order` that is not a number, two headings that make the same anchor, and an unknown callout marker such as `[!NOTES]`. `check` counts them and exits with 1 on any `error`, the build prints them and does not fail. A missing image and a bad `order` are errors, the rest warnings, and the new `check` key in `sitekit.config.json` sets each kind to `error`, `warning` or `off`; a name that is not a kind fails with the name in the message. Links, images, headings and markers inside code are never reported. The warnings that `loadSite` collected while rendering, and that nothing printed, are replaced by these findings. A site generated earlier gets the findings in `check` at once, because the CLI reads them, and in the build once it copies the changed files of `template/src/` and `astro.config.ts` from this version. See `docs/content.md`.

### Changed

- **The project site announces `https://miguelcolmenares.com/docs-sitekit/` as its address**, in its canonical links, its sitemap and its `llms.txt`. The personal domain serves the site through a proxy, and GitHub Pages keeps answering at the old address. A site generated with `init` is not affected.
- **The default accent is the VS Code blue**: `accent` `#4fc1ff`, `accent-strong` `#007acc` and `accent-contrast` `#ffffff`, in place of the purple. A site generated with `init` takes the blue from the kit it is generated with. A site generated earlier keeps its own `design/tokens.json`, so it stays purple until its owner changes that file.
- **The Action's Marketplace icon is blue**, `branding.color` in `action.yml`, to match the new default accent. Blue is the closest color the Marketplace offers to the VS Code blue.

### Fixed

- **The name of the tool is `docs-sitekit` everywhere a reader sees it.** The footer of every generated site, the Action address, its name, the issue forms, the contributing steps and the help text used the old short name. The `sitekit` command and the file names do not change. A test reads these texts and fails on the old name. The Action address in the 0.1.0 notes is corrected too.

## [0.1.1] - 2026-10-28

### Fixed

- **Two CodeQL findings in `describe.ts`**, the file that turns markdown into titles and descriptions and that every generated site carries. Removing HTML tags in a single pass left a `<script` behind when tags were nested, so tags are now removed until the text stops changing. The check for a row of badges used a nested repetition that could backtrack exponentially on a long run of badge-like text, and now removes each badge with a single pattern. Both have regression tests. A site generated with 0.1.0 can copy `describe.ts` from this version.
- The project site is served under `/docs-sitekit/`, where it was still asking for its assets under the old repository name. A test now ties the site's base path, address and repository to `package.json`.

## [0.1.0] - 2026-10-28

First release. The package is `docs-sitekit` and the action is `miguelcolmenares/docs-sitekit`. The `sitekit` command is the one you run: `npx docs-sitekit init`.

### Added

- `sitekit init`, `check`, `list` and `add`. `init` reads `package.json` and the git remote, finds `docs/`, `docs/tutorials/`, `docs/examples/` and `examples/`, writes the site and a GitHub Pages workflow, and refuses a folder that already has files.
- **Collections and groups.** A site has any number of collections (Docs, Tutorials, Examples). A page belongs to the collection with the deepest folder, so `docs/tutorials/` can sit inside `docs/`. Pages can be put in groups with a tone, and a page that is in no group, or a group that names a page that does not exist, fails the build instead of being skipped.
- **A reusable GitHub Action** (`miguelcolmenares/docs-sitekit`) that installs, builds and checks a site and uploads it as the Pages artifact. The workflow `init` writes uses it and rebuilds the site when a release is published. Deploying stays in a separate job.
- A dark design system on Astro, Tailwind, shadcn/ui and lucide-react: tokens, header, hero, section headers, cards, feature grid, flow diagram, command table, callouts, footer, doc layout with table of contents, and copy buttons. Tokens come from one file, and contrast is tested on them.
- A content pipeline that turns markdown into pages, derives titles and descriptions without being fooled by badges, tables or code fences, rewrites relative links, and fails on two files that would get the same route.
- The version in the footer is read from the repository's `package.json` on every build, so a site rebuilt for a release shows the release.
- A publish check, `sitekit check`: credentials and internal hosts in the content and in the built files, the repository's visibility (a private repository's Pages site is public), and the shape of the output, including a `404.html` that is not a copy of `index.html`.
- Pack-and-install verification, and Playwright tests on a phone (320, 360 and 390 px) and a desktop: WCAG AA contrast measured in the browser, touch targets, scrollable code blocks and tables that can be focused, no horizontal scroll, keyboard use, and accessibility checks.
- Security policy, contributing guide, issue and pull request templates, and third-party notices.
